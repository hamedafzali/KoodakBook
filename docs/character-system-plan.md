# Interactive Character System — Technical Plan

**Status:** design (no code changed). Builds on: audio pipeline (per-voice
ElevenLabs generation + caching), scene library, animation registry (mig 014),
AI provider layer (stories/translation, admin prompts, daily caps), placement
strand levels, speech recognition lib, plans/entitlements, «نارنج» design kit.

| Question | Answer |

**Integration verdict: no rebuild.** Every subsystem a character system needs
already exists as a data-driven pattern (voices → `audio_sections`, scenes →
`SCENE_SLUGS`, animation → `animation_template`+params, AI → provider layer
with admin prompts + caps). Characters become one more data-driven registry.

## §2 Character architecture (data-driven)

**Migration: `characters` + `character_lines` + `conversations`.**

```sql
create table characters (
  id            uuid primary key default gen_random_uuid(),
  slug          text unique not null,          -- 'simorgh', 'roozi'
  name_persian  text not null,                 -- «سیمرغ», «روزی روباهه»
  type          text not null check (type in ('child','animal','fantasy')),
  personality   text not null,                 -- prompt fragment: «بامزه، کنجکاو، صبور»
  age_band      int  not null default 1,       -- 1..3 (design-system bands)
  level         int  not null default 1,       -- Persian level 1..4 (strands)
  voice_engine  text not null default 'elevenlabs',
  voice_id      text not null,                 -- ElevenLabs voice per character
  animation     jsonb not null default '{}',   -- {engine:'svg'|'rive', asset, states:[...]}
  topics        text[] not null default '{}',  -- word categories (existing enum)
  teaching_role text not null,                 -- 'vocabulary'|'stories'|'phonics'|'conversation'
  home_scene    text not null default 'garden',-- scene-library slug
  system_prompt text not null,                 -- character card for the LLM (server-side only)
  is_active     boolean not null default true
);

create table character_lines (                  -- V1: scripted, pre-recorded
  id uuid primary key default gen_random_uuid(),
  character_id uuid references characters(id) on delete cascade,
  trigger  text not null,   -- 'greeting'|'praise'|'retry'|'lesson_intro:animals'|'story_open'…
  text_persian text not null,
  audio_url text,           -- generated by the EXISTING regen pipeline (new 'character' scope)
  emotion  text not null default 'happy'        -- drives animation state
);

create table conversations (                    -- V2: logged AI turns (parent-reviewable)
  id uuid primary key default gen_random_uuid(),
  child_id uuid references children(id) on delete cascade,
  character_id uuid references characters(id),
  role text not null check (role in ('child','character')),
  text text not null,
  created_at timestamptz not null default now()
);
```

Example row — **Roozi the Fox** (روزی روباهه): type `animal`, personality
«بامزه، کنجکاو، صبور», role `vocabulary`, level 1, topics
`{animals,colors,family,food}`, voice = a playful ElevenLabs voice_id,
home_scene `forest`. **Character #1 is the existing Simorgh** — formalized,
named, given a voice; zero new art debt for V1.

Progress/rewards reuse existing tables: friendship level per character = a
`child_character` row (xp, level) feeding the existing badge system;
vocabulary practice writes to `child_word_progress` exactly like lessons do.
Stories link via `stories.character_id` (narrator + host).

## §3 Technology choices (grounded, opinionated)

**Character creation/art.** Same policy as photos/scenes: AI-generate
candidates ONCE, human-curate, commit as layered SVG (or Rive file) matching
the «نارنج» style guide. Never runtime-generated character images —
consistency is the whole game. Assets live in the repo (like scenes), not
uploads. Consistency tool: one reference sheet per character (front, 3/4,
emotions) generated in a single session, then all future art derives from it.

**Animation — 2D vector wins, 3D rejected.** 3D (three.js/Unity-web) costs
10× in assets, loading, and battery for a children's PWA and fights the flat
design language. Ladder: **V1 = layered SVG + framer-motion** (exactly the
Simorgh pattern: mood → transform animation; extend to 5 states: idle, happy,
encouraging, thinking, celebrating). **V2 = Rive** (already in
`ANIMATION_ENGINES`): one `.riv` per character with a state machine (inputs:
`emotion`, `talking`); ~50KB, 60fps, designer-editable without code.
**Lip-sync: viseme-lite only** — drive a `talking` boolean + mouth-open
amplitude from the playing clip's volume (Web Audio AnalyserNode on the same
`Audio` element the speech lib already tracks). Full phoneme lip-sync is
uncanny-valley effort with near-zero payoff at this art style.

**Voice.** Per-character **ElevenLabs voice_id** — the pipeline already
supports arbitrary voices per section; characters are "sections with faces."
Scripted lines pre-generate through a new `character` regen scope (same
missing-mode economics: one-time cost). AI replies (V2) synthesize on demand
and **cache by hash(character_id + text)** — constrained outputs repeat
heavily, so the cache hit-rate is high. STT: existing Web Speech
(`lib/recognition`, already powering the speak page) for V2; upgrade path to
Whisper API server-side when reliability data demands it (premium feature
absorbs the cost).

**AI conversation.** Existing provider layer (Anthropic/OpenAI-compatible,
admin-configurable, capped) — no new vendor. See §4.

**Backend storage** — see §2; nothing new beyond three tables. Audio files on
the uploads volume like everything else; conversations table gives parents an
auditable transcript (trust feature) and us tuning data.

## §4 Controlled conversation engine (V2) — not open-ended chat

Pipeline per turn:

```
child audio ──STT──▶ text ──▶ [Turn Planner] ──▶ [LLM, constrained] ──▶ [Validator] ──▶ TTS(character voice, cached) + emotion tag ──▶ Rive state
```

1. **Turn Planner (deterministic, no LLM):** picks the pedagogical frame for
   this turn — `praise → recast → follow-up`. Recast is the core method: the
   character repeats the child's meaning in correct, slightly richer Persian,
   never says "wrong". Child: «من سیب دوست دارم» → frame output for the LLM:
   *praise + recast + one follow-up question using only allowed vocab*.
2. **LLM call, tightly boxed:** system prompt = character card (from the DB
   row) + child's strand levels (placement data) + allowed vocabulary (the
   word catalog filtered by character topics + child stage) + hard rules:
   Persian only, max 2 short sentences, end with a question, no names/places/
   personal questions, no promises, no external references.
3. **Validator (server-side, deterministic):** reject/regenerate if output is
   >2 sentences, contains Latin script/URLs/digits beyond ۰-۹, uses words
   outside stage+2 vocabulary (tokenized check against the words table), or
   trips a banned-topic list. Failed twice → fall back to a scripted
   `character_lines` response. **The child never sees a raw model failure.**
4. **Safety posture:** prompts live server-side only; conversations logged
   for parent review; no PII in prompts (first name only, the same policy as
   story generation); response length caps double as cost caps; per-plan
   daily conversation caps reuse the `ai_stories_per_day` pattern
   (`conversations_per_day` plan feature).
5. **Difficulty adaptation:** the planner reads the child's level like the
   story generator already does; level drives sentence length, vocab filter,
   and how much of the recast expands the child's sentence.

Example turn: child «من سیب دوست دارم» → character (level 1): «آفرین! منم
سیب دوست دارم! 🍎 سیبِ قرمز دوست داری یا سبز؟» — praised, recast with an
adjective expansion, follow-up binary question (easy to answer, teaches
colors — Roozi's topic).

## §5 UX design

- **Introduction:** first home visit → the character walks in over its
  `home_scene` backdrop, waves, speaks a pre-recorded greeting («سلام! من
  روزی‌ام!»). Chunky «سلام کن!» button = the child's first reply (tap, not
  speech — zero-pressure onboarding).
- **Character home:** `/child/friends/[slug]` — the character in its scene,
  friendship hearts, 3 chunky doors: «حرف بزنیم» (talk), «بازی» (its
  vocabulary game, filtered to its topics), «قصه بگو» (its story library).
- **Talk interface:** character fills the top half (Rive/SVG, reacts live);
  one giant push-to-talk mic (band-1 sized); child's recognized words render
  as chips; character replies with voice + emotion + text. No free-text
  keyboard for kids.
- **Vocabulary games:** existing quiz/memory engines gain an optional `host`
  — the character presents, praises (its own pre-recorded praise lines) and
  reacts to wrong answers with encouragement. Zero new game code.
- **Story mode:** stories with `character_id` are narrated in that
  character's voice (pipeline supports per-story voice trivially) and the
  character appears on the story shelf as the "author".
- **Rewards/growth:** friendship level per character (hearts) → unlocks new
  reactions, a hat/scarf (SVG layer toggles), and that character's next
  story. Growth is *relationship depth*, not stat inflation.

## §6 Future-proofing / roadmap

**V1 (1–2 weeks):** `characters` + `character_lines` tables, admin CRUD page
(clone of the audio-sections pattern), `character` regen scope for line
audio, Simorgh formalized + Roozi added, character home + hosted games +
greeting flow. All scripted, all pre-recorded, SVG animation.
**V2 (1–2 months):** conversation engine (§4) behind a premium flag +
`conversations_per_day`, push-to-talk UI, Rive migration of the two
characters, friendship levels, parent transcript view.
**V3 (quarter+):** multi-character scenes in stories, seasonal guest
characters (Haji Firuz at Nowruz — content op, not code), character-specific
curricula, and the character picker as the app's front door.

**"Adding a character requires minimal coding" — the test:** a new character
must be exactly (1) one INSERT (or admin form), (2) one ElevenLabs voice_id,
(3) one SVG/Rive asset, (4) one batch of `character_lines` rows + a regen
click. If any step needs a code change, the abstraction has failed. This is
the same bar the audio sections, scenes, plans, and animation registry
already meet — characters inherit the house pattern.
